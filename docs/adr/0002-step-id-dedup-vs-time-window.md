# 0002: Step ID Deduplication vs Time Window

## Context

При обработке multiple `human-gate` событий возникает проблема дублирования нотификаций. Если несколько human-тикетов переходят в состояние `ready` одновременно (например, после approve первого из пяти), пользователь получает дублирующие уведомления. Необходимо выбрать стратегию дедупликации.

## Considered Options

### Option A: 60-second TTL (time-based window)

Использовать time-based bucket: все нотификации, произошедшие innerhalb 60 секунд, группируются в одну.

**Pros:**
- Простая реализация
- Не требует хранения состояния между нотификациями

**Cons:**
- Может "проглатывать" легитимные нотификации: если 5 human-тикетов готовы после approve первого, они все могут попасть в один 60-секундный window
- Слишком грубый подход для burst-сценариев

### Option B: step_id-based equivalence (hour-bucket)

Дедуплицировать на основе `step_id` или hour-bucket: нотификации с одинаковым/сгруппированным идентификатором шага объединяются.

**Pros:**
- Точечная дедупликация именно по step_id
- Не теряет нотификации при разных тикетах
- Более предсказуемое поведение

**Cons:**
- Требует понимания структуры step_id
- Сложнее реализации

## Decision

**Выбрано Option B: step_id-equivalence (hour-bucket).**

Дедупликация реализуется через группировку по `step_id` (или hour-bucket). Это решает проблему сценария, когда 5 human-тикетов становятся ready после approve первого — они будут дедуплицированы как belonging к одному logical group, без потери individual нотификаций, но при этом не вызовут flood.

Использование pure 60-sec TTL отвергнуто, так как оно "проглатывает" legitimate нотификации при 5+ simultaneous gates.

## Consequences

### Positive
- Более точная дедупликация без потери важных нотификаций
- Учёт группировки тикетов по step_id/hours обеспечивает семантически корректное объединение
- Решает проблему burst-уведомлений

### Negative
- Более сложная реализация по сравнению с простым TTL
- Требуется корректное извлечение и нормализация step_id

### Risks
- Ошибка в логике группировки может привести к неполной дедупликации или наоборот — к потере нотификаций
- Нужна thorough testing edge-сценариев
