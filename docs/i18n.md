# Internationalization (i18n) Guide

This guide provides instructions for contributors who are adding or updating translations in the project.

## 1. Structure of l10n Files

The project uses the following localization file structure:

### Bundle Files
- `l10n/bundle.l10n.json` - English source file
- `l10n/bundle.l10n.{locale}.json` - Translation files for different locales

### Package NLS Files
- `package.nls.json` - English source file
- `package.nls.{locale}.json` - Translation files for different locales

### Supported Locales
The following locales are supported:
- de (German)
- es (Spanish)
- fr (French)
- it (Italian)
- ja (Japanese)
- ko (Korean)
- pt (Portuguese)
- pt-br (Brazilian Portuguese)
- ru (Russian)
- zh (Chinese)
- zh-cn (Simplified Chinese)
- zh-tw (Traditional Chinese)

## 2. Placeholders

### Format
Placeholders follow the format: `{0}`, `{1}`, `{name}`

### Important Rules
- Placeholders must be preserved in all translations - never remove them
- All placeholders in the English source must have corresponding placeholders in translated versions
- Maintaining placeholder parity is critical for proper functionality

### Example of Failure
If the English text is: `'Ticket {0} after {1} attempts'`
And a locale translation loses `{1}` and becomes: `'Ticket {0} after attempts'`
This will fail the parity-check

## 3. Running Parity-Check Locally

### Command
```bash
npm run lint:l10n
```

### Understanding Errors
The parity-check will identify:
- Missing placeholders in translated files
- Extra placeholders that don't exist in the English source
- Incorrect placeholder ordering
- Missing translation files for supported locales

### Common Fixes
1. **Missing placeholders**: Add the missing placeholder to the translation file
2. **Extra placeholders**: Remove placeholders that don't exist in the English source
3. **Wrong ordering**: Reorder placeholders to match the English source
4. **Missing locale files**: Create translation files for any missing supported locales

## 4. Workflow for New Features Requiring Translations

When adding new functionality that requires translations for 11 locales:

### Step 1: Add English Key
Add the new English key to `bundle.l10n.json`

### Step 2: Machine Translation
- Use machine translation (Claude, DeepL) to translate the key for 11 locales
- Add translations to `bundle.l10n.{locale}.json` files
- Mark the commit with `[needs review]` in the commit message

### Step 3: Manual Review
- Create an issue for manual proofreading by native speakers
- Target locales for native review: de, es, fr, ja, zh-cn
- Request native speakers to review and improve the machine-translated content

### Step 4: Update Package NLS Files
- Add the English key to `package.nls.json`
- Add translations to `package.nls.{locale}.json` files
- Run parity-check to ensure consistency

### Step 5: Final Validation
- Run `npm run lint:l10n` to verify all translations are correct
- Update any issues identified by the linter
- Remove `[needs review]` marker from commit message after review is complete

## Best Practices

1. **Test with Different Locales**: Always test your changes with different locales to ensure UI elements display correctly
2. **Keep Placeholders Consistent**: Use the same placeholder names across related strings when possible
3. **Context Matters**: Provide context when requesting translations to ensure accuracy
4. **Update Documentation**: Update this guide if you encounter new patterns or requirements
5. **Use Consistent Terminology**: Maintain consistent terminology across all locales

## Troubleshooting

### Common Issues
- **Missing translations**: Ensure all supported locales have the key
- **Placeholder mismatches**: Check that all placeholders are preserved and in the correct order
- **Encoding issues**: Ensure JSON files are saved with UTF-8 encoding
- **Special characters**: Verify that special characters are properly escaped in JSON

### Getting Help
- Check existing translations for patterns
- Consult with the team for complex translation requirements
- Use translation memory for consistency across similar strings
